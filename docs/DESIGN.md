# CROWD RUNNER — 설계안 v0.1 (2026-10-08)

> 받은 기획서(`GDD v1.0`)는 **무엇을 만들 것인가**를 이미 충분히 적었다. 이 문서는 그 위에서
> **어떻게 지을 것인가**만 정한다 — 기획서를 옮겨 적지 않는다. 옮겨 적으면 두 벌이 되고,
> 두 벌은 반드시 어긋난다.
>
> 그래서 여기 있는 것은 셋뿐이다: **먼저 증명할 것** · **구조를 가르는 선 하나** · **지금 정해야 할 것**.

---

## 0. 경계 — 무엇을 가져오고 무엇을 안 가져오는가

기획서가 이미 적어 둔 선을 **구속력 있게** 다시 적는다. 이 줄을 넘는 작업은 하지 않는다.

| | |
|---|---|
| **가져온다** | 메커니즘 — 자동 전진 · 좌우 조작 · 증식 게이트 선택 · 군단 자동 전투. **게임 규칙은 저작권의 대상이 아니다** |
| **안 가져온다** | 캐릭터 · UI 레이아웃 · 아이콘 · 색 조합 · 맵 · 레벨 수치 · 이름 · 상표. **스크린샷을 옆에 놓고 맞추는 작업을 하지 않는다** |
| **프로젝트 이름** | `crowd-runner` — 장르다. 원작 이름을 폴더·클래스·에셋·빌드 이름 어디에도 쓰지 않는다 |

> 참고 이미지는 **"이런 종류의 게임"** 을 가리키는 용도까지다. 수치는 전부 우리가 정하고,
> 그 근거는 우리 플레이테스트에 둔다 (기획서 §16 "실제 탑워 내부 데이터가 아니라 설계값" 과 같은 입장).

## 1. 먼저 증명할 것 — **M0: 500명이 도는가**

기획서 §16 이 *"기본 아트 제작보다 군단 렌더링 및 이동 테스트를 먼저"* 라고 적었다. 그 말이 맞고,
**그보다 더 앞으로 당긴다.** 아트도 UI도 레벨도 게이트도 없이, 이것 하나만 되는 빌드를 먼저 만든다.

```
M0 통과 조건 (v0.2 — 세션 B 가 넷을 고쳤다, 2026-10-08)
  기기: SM-G991N (갤럭시 S21 · Exynos 2100 · Android 15) — 지금 붙어 있는 유일한 실기

  · 1,000 개체를 **출하할 방식 그대로** 그린다 — 애니메이션 포함. **캡슐이 아니다**
  · 군중(그리기 + 유닛당 더미 계산)이 프레임의 **≤ 8 ms**
  · **p99 프레임 ≤ 중간값 × 2** — 증식 프레임을 포함해서
  · 군중 경로의 프레임당 **관리 힙 할당 0 B**
  · 10 분 연속에서 상주 메모리 기울기 ≈ 0
```

### v0.1 의 조건이 틀렸던 자리 넷 — 기록해 둔다

내가 처음 쓴 것은 *"캡슐 1,000 개 · 실기 30fps · 멈춤 없음"* 이었다. 넷 다 틀렸고, 왜 틀렸는지가
다음 관문을 세울 때 또 쓰인다.

| | 틀린 것 | 왜 |
|---|---|---|
| **①** | *"캡슐 하나로 충분하다"* | 출하할 군중은 **스킨드 메시 + 애니메이션**이고 캡슐과 **자릿수가 다르다.** 캡슐이 도는 것은 *트랜스폼과 드로우 경로가 멀쩡하다*는 뜻일 뿐이다 — **이 게임이 도는가에는 아무 답도 안 한다.** 캡슐로 통과시키고 스킨드로 바꿔 12 fps 가 나오면 M0 가 막으려던 4 주를 **그대로 치른다**. 관문이 제 일을 안 한 것이다 |
| **②** | *"30 fps"* | M0 에는 UI·VFX·사운드·지형·게이트·전투가 **하나도 없다.** 빈 장면에서 정확히 30 이면 완성본은 30 아래다. fps 가 아니라 **프레임 예산의 몫**으로 잡아야 한다 |
| **③** | *"눈에 띄는 멈춤 없음"* | **문장이라 측정이 안 된다.** 수백 개체가 한 프레임에 생기는 순간이 최악값이고, 드래그 게임에서 긴 프레임 하나는 평균 5 fps 보다 나쁘게 느껴진다 → **p99** |
| **④** | 전투 규칙을 M0 에서 뺀 것 | 1,000 개체의 비용은 그리는 것보다 **서로를 찾는 것**에서 더 날 수 있다 (두 군단이 겹치는 순간). 유닛당 계산 자리를 비워 두면 **예산을 전부 렌더링에 써 버리고**, M1 이 붙을 때 다시 떨어진다 → 더미라도 유닛당 O(n) 한 번을 넣고 잰다 |

> **①은 어제 좀비퀸 `HANDOFF.md` §0c-12 로 적어 둔 것과 같은 모양이다** — *"옆에 있던 다른 증거가
> 검사를 대신 통과시킨다."* 관문을 세우는 쪽이 그 함정에 빠지면 관문 전체가 장식이 된다.

### 8 ms 의 근거 (그리고 그 근거의 약점)

S21 의 GPU 는 저가 보급기(2023 년 Snapdragon 4 급)의 **대략 3~4 배**다. S21 에서 8 ms 면 바닥
기기에서 24~32 ms — 거기서 **겨우** 30 fps 이고 그것도 아직 아무것도 안 붙은 상태다. 그리고
8 ms 는 16.6 ms 의 절반이라 **M0 가 담지 않은 전부에 나머지 절반**을 남긴다.

⚠ **이 3~4 배는 추정이다.** 지금 붙어 있는 기기가 **2021 플래그십 하나뿐**이고 바닥 기기가 없다.
싼 폰이 한 대 생기면 **그 배율을 실측으로 바꾼다** — 그때까지 8 ms 는 *"근거 있는 임시값"* 이지
측정값이 아니다. 오너께 여쭐 자리다.

### M0 의 진짜 질문은 **"군중을 어떻게 그릴 것인가"** 다

위 조건을 만족하려면 방식을 골라야 하고, 그 선택이 곧 M0 다:

- **GPU 인스턴싱 + 정점 애니메이션 텍스처** (본 없이 구운 것) — 개체당 비용이 거의 없다. 대신 굽는
  파이프라인이 필요하고 개체별 변형이 어렵다
- **유닛마다 `Animator`** — 만들기 쉽고 변형이 자유롭다. 대신 수백 개에서 무너진다

둘을 **같은 장면에서 나란히 재서** 고른다. 캡슐은 1 주차 배선 확인용으로는 여전히 쓸모 있지만
**관문이 될 수 없다.**

**M0 에서 만들지 않는 것**: 게이트 · 전투 규칙 · 레벨 · UI · 아트 · 사운드. 캡슐 하나로 충분하다.

## 2. 구조를 가르는 선 하나 — **로직과 표현을 분리한다**

이 설계안에서 가장 중요한 한 줄이다. 기획서 §8 의 네 매니저보다 **이 선이 먼저**다.

```
[ 로직 ]  순수 C# · Unity 타입 없음 · 결정적 · 렌더링 없이 혼자 돈다
            병력 수 · 게이트 효과 · 전투 손실 · 진행 거리 · 승패

[ 표현 ]  MonoBehaviour · 보간 · 파티클 · 소리 · 카메라
            로직이 정한 수를 **보여 주기만** 한다
```

### 왜 이렇게 가르는가 — 이득이 셋이다

**① 레벨을 자동으로 검증할 수 있다.** 기획서 §6.4 와 §12.2 가 *"가능한 게이트 조합을 분석"* ·
*"클리어 가능한 경로 수 자동 출력"* 을 요구한다. 로직이 Unity 없이 돌면 **에디터를 켜지 않고**
한 레벨의 모든 경로(2ⁿ)를 밀어 보고 *최적/일반/실패* 경로를 뽑을 수 있다. 섞여 있으면 그 도구는
못 만든다 — 레벨을 사람이 손으로 열 번 플레이해서 감으로 맞추게 된다.

**② 밸런스를 숫자로 비교할 수 있다.** 레벨 수치를 바꿨을 때 *무엇이 어떻게 달라졌는지*를
표로 본다. 이게 없으면 "좀 쉬워진 것 같다" 로 조정하게 되고, 그건 되돌릴 수도 없다.

**③ 성능 문제와 규칙 문제가 섞이지 않는다.** 프레임이 떨어졌을 때 *계산이 무거운 건지 그리는 게
무거운 건지*가 바로 갈린다. M0 의 500 명 검증도 이 선이 있어야 **표현만** 바꿔 가며 잴 수 있다.

### M0 가 떨어질 때를 위한 보험 — `Core/` 는 **개체 하나를 모른다**

*"M0 결과가 M1 설계를 바꾸지 않는다"* 는 **절반만 맞다** (세션 B 지적). M0 가 떨어지면 대안이
*"개체를 논리값으로만 들고 화면은 추상화"* 인데, 그건 유닛 모형이 **「N 개의 개체」에서 「하나의 수」로**
바뀌는 것 — **로직 쪽 변경**이다.

그래서 규칙 하나를 지금 건다: **`Core/` 어디에서도 개체 하나의 정체성(id · 개별 좌표 · 개별 HP)을
전제하지 않는다.** 병력은 **수**이고, 전투는 **수의 감소**다. 개별 유닛은 **표현 쪽에만** 있다.
지금은 공짜이고 나중엔 비싸다 — M0 가 어느 쪽으로 떨어져도 M1 은 그대로 선다.

### 선을 지키는 규칙

- 로직 폴더(`Core/`)는 **`UnityEngine` 을 `using` 하지 않는다.** 벡터·난수도 자체 타입을 쓴다
  (좀비퀸에서 `tools/SpawnCheck` 가 `Core`·`Data` 만 net8 로 컴파일해 검사기를 돌리는 것과 같은 장치 —
  **컴파일이 규칙을 강제한다**. 사람이 지키는 규칙은 지켜지지 않는다)
- 로직은 **고정 스텝**으로 돈다 (`Step(dt)` 하나, `dt` 는 항상 1/60). 프레임이 떨어져도 결과가 같다
- 난수는 **시드를 받는다.** 같은 레벨 + 같은 입력 = 같은 결과. 이게 ①②의 전제다

## 3. 기획서에서 **고쳐야 할 자리** 셋

읽으면서 그대로 가면 나중에 비싸질 자리만 짚는다.

### 3.1 전투 모델이 **둘**이다 — 하나로 만들거나, 검사기를 둔다

기획서 §4.3 은 개별 유닛 전투(타이머·사거리·피해)를, §4.5 는 추상식
`P_remain = max(0, P − ⌈E×k⌉)` 를 적고, **"두 방식의 결과가 크게 어긋나면 보정한다"** 고 했다.

> **"어긋나면 보정한다" 는 아무도 안 한다.** 어긋났다는 것을 말해 주는 것이 없기 때문이다.

택할 길은 둘이다:

| | |
|---|---|
| **A. 추상식을 버린다** | 레벨 검증도 개별 전투 시뮬로 돌린다. 느리지만 **진실이 하나**다 |
| **B. 둘 다 두고 검사기를 붙인다** | 레벨마다 두 모델을 돌려 **잔여 병력 차이가 N% 를 넘으면 실패**시킨다 |

**B 를 권한다.** 추상식은 레벨 설계 중에 수천 번 돌려야 해서 빠른 쪽이 필요하고, 개별 전투는
화면에 나올 진짜다. 다만 **둘이 따로 자라지 않게 묶는 장치**가 없으면 B 는 A 보다 나쁘다.

### 3.2 게이트 판정을 `OnTriggerEnter` 로 하지 않는다

기획서 §9.2 의 예제는 물리 트리거 + `GateGroupManager.Instance` 싱글턴이다. 둘 다 바꾼다:

- **물리 트리거는 프레임 의존적이다.** 고정 스텝 로직 안에서 *"리더의 z 가 게이트 z 를 넘었는가"* 로
  직접 판정한다 — 빠르고, 결정적이고, Unity 없이 돈다
- 게이트는 **그룹 단위로 한 번만** 발동한다. 그룹이 상태를 들고, 통과 즉시 잠근다.
  기획서가 짚은 *"왼쪽 병력은 +50, 오른쪽 병력은 ×3 에 동시에 닿는다"* 는 **리더 중심 판정**으로
  해결되고, 그건 로직 쪽에 있어야 성립한다

### 3.3 "슬롯 번호 = 배열 순서" 를 처음부터 피한다

기획서 §9.3 이 스스로 지적했다 — 유닛이 죽을 때마다 뒤 유닛이 자리를 바꾸면 **군단 전체가
꿈틀거린다.** 처음부터 **슬롯 ID 를 유닛이 들고, 빈 슬롯을 재사용**하는 쪽으로 간다. 나중에
고치려면 대형·전투·렌더링이 전부 그 가정 위에 얹혀 있어서 비싸다.

## 3b. 바깥은 좀비퀸 그대로, 안쪽만 새로 만든다 (오너 2026-10-08)

오너 지시 둘:

> *"맵은 좀비퀸 맵 재활용할게 — **맵 선택 화면**을 말하는 거야. **부산부터 시작하는** 우리가
> 만들어 놓은 좀비퀸 화면"* · *"좀비화된 세계를 쓸어버리는 게 목표"*

즉 **메타 껍데기는 통째로 가져오고, 한 판의 속만 바꾼다.**

| | |
|---|---|
| **가져온다 (그대로)** | **월드맵 화면** (`GameFlow.WorldMap.cs` — 도시 그림 위에 스테이지, 탭하면 스테이지 카드) · **도시 = 10 판** 구조 (`Cities` · `Stages.StagesPerChapter`) · **정복 진행**(`Progress` — 구역 클리어·☣ 등급·도시 100%) · 부산부터 시작 · 결과/패배 화면 · 톤과 색 |
| **새로 만든다** | **한 판의 속.** 좀비퀸은 2D 마을을 돌아다니지만, 여기서는 같은 스테이지를 누르면 **러너 레인**이 뜬다 |

```
[월드맵: 부산]  ← 좀비퀸 그대로
      ↓ 스테이지 1-3 탭
[스테이지 카드]  ← 좀비퀸 그대로
      ↓ 시작
[러너 한 판]     ← 여기만 새로 만든다  (자동 전진 · 게이트 · 군단 전투)
      ↓
[결과 · ☣ 등급]  ← 좀비퀸 그대로 → 월드맵으로
```

**이 구조의 이득이 크다.** 이 장르의 약점은 기획서 §14 가 짚은 *"건설과 RPG 를 빼면 장기 동기가
약해진다"* 인데, **정복 지도가 그 자리를 메운다** — 한 판이 1~2 분이고 도시가 10 판이면
*"부산을 쓸어 간다"* 가 진행의 뼈대가 된다. 메타를 새로 설계할 필요가 없고, **이미 돌아가는 것**이다.

### 그래서 레벨 번호를 그 구조에 맞춘다

`LevelData` 는 `chapter`(도시) · `index`(1~10) 를 들고, 월드맵이 그 둘로 판을 찾는다.
**좀비퀸의 `Stages` 자리에 러너 레벨이 들어가는 모양**이다. 번호 체계가 다르면 월드맵을
그대로 못 쓰고, 그러면 가져온 이득이 사라진다.

### 안쪽은 왜 못 가져오나 (한 줄로)

좀비퀸의 **맵 데이터**(`MapDef` — `w × d` 2D 마을, 도로·건물·사람·순찰)는 플레이어가 **어디로든**
갈 수 있다는 전제로 지어졌다. 러너의 레벨은 **z 한 줄에 줄 세운 사건**이다. 그래서 `Maps.cs` 는
읽지 않는다 — 읽으면 도달성·순찰·시야 같은 **1D 에 뜻이 없는 전제가 코드로 따라 들어온다.**
다만 **건물·소품 킷과 좀비 모델·애니메이션은 그대로 쓴다** (레인 양옆을 그 킷으로 채우면
*"좀비 도시를 쓸고 지나간다"* 가 아트 제작 없이 나온다).

### 이 결정이 바꾸는 것

- **적 = 좀비.** 느리지만 많다 — 기획서 §4.2 의 적 이동 3.0 m/s 를 좀비 속도로 다시 잡는다
- **아군 = 생존자·군대.** 좀비퀸의 시민·경찰·소방관 모델이 그대로 아군이 된다
- **최종 방어선**은 좀비 무리. 보스 자리에 좀비퀸 보스를 쓸 수 있다 (2 차)
- 톤은 좀비퀸을 따른다 (피는 보라/분홍, 불·HP 바만 빨강). **두 게임이 같은 세계로 보이는 것이
  손해가 아니다** — 월드맵을 공유하니 오히려 그래야 맞다

## 3c. 첫 시뮬이 잡은 것 — **지금 구조로는 "큰 숫자가 늘 정답" 이다** (2026-10-08)

`tools/sim` 이 돌기 시작하자마자 셋이 나왔다. 셋 다 **코드를 읽어서는 안 보이는 것**이고,
기획서의 예시 수치를 그대로 넣었기 때문에 나온 것이다.

### ① 기획서 §6.4 의 예시 레벨은 **못 깬다**

그 숫자(시작 10 · `+30`/`×3` · 적 20 · 벽 · `+50`/`×2` · 최종 80)를 그대로 돌리니
**네 경로가 전부 실패**했다. 최선인 `LL` 도 최종 전투 앞에서 70 명이라 80 을 못 넘는다.
예시는 *설명용*이지 밸런스가 아니었고, **그걸 확인하는 데 1 초 걸렸다** — M4 를 M5 앞에 둔 이유다.

### ② 적과 아군의 수치가 같으면 **모든 레버가 죽는다**

처음에 좀비를 아군과 똑같이 두었더니 네 경로의 손실 계수가 **정확히 1.00** 이었다.
같으면 양쪽이 같은 속도로 죽어서 **생존자 = 아군 − 적** 이 되고, 그러면 **전선 폭도 공격 간격도
결과에 아무 영향이 없다** (싸우는 *시간*만 바뀐다). 좀비를 *느리고 약하지만 많게* 둔 것은
세계관이기도 하지만, **모델이 일을 하기 시작하는 조건**이기도 하다.

### ③ ⚠ 그런데 지금 구조에서는 **큰 숫자를 고르는 것이 늘 정답이다**

고친 수치로 다시 돌리니 **네 경로가 전부 클리어**된다. 그리고 더 중요한 것:

```
| 경로 | 잔여 | 전사 | 적 처치 |  k  | 시간  |
|  LL  |  50  |  40  |   100   | 0.40| 47.1s |
|  RL  |  40  |  40  |   100   | 0.40| 47.1s |
|  LR  |  33  |  40  |   100   | 0.40| 47.1s |
|  RR  |  13  |  40  |   100   | 0.40| 47.1s |
```

**전사·처치·시간이 네 경로에서 똑같고 잔여만 다르다.** 이유는 전선 폭이다 — 길이 7 m 면 한 번에
7 명씩만 싸우므로, **병력이 그 이상이면 더 있어도 덜 죽지 않는다.** 많으면 *버틸* 뿐이다.

> 즉 **병력이 많은 것에 대가가 없다.** 그러면 플레이어는 늘 큰 수를 고르면 되고, 기획서 §3.4 가
> *"가장 큰 숫자를 고르는 것만으로 항상 정답이 되어서는 안 된다"* 로 금지한 상태가 된다.

**전투 모델을 고쳐서 풀 문제가 아니다** — 전선 폭이 저렇게 도는 것은 맞다(1,000 명이 동시에 서로
때리지는 않는다). **레벨 쪽에서 풀어야 한다.** 기획서 §6.3 이 이미 답을 적어 뒀다:
*"`×3` 게이트 뒤에 방어벽이 있고 `+70` 게이트 뒤에는 적이 적은 경로"*.

그러려면 **사건이 어느 쪽 길에 붙는지**를 데이터가 알아야 한다 — 지금은 게이트만 좌우가 있고
적·벽은 길 전체를 막는다. `LevelEvent` 에 `lane` 을 두면 1D 구조를 유지한 채 *"오른쪽으로 가면
벽, 왼쪽으로 가면 적이 더 많다"* 가 표현된다. **다음 단위로 그걸 넣는다.**

## 3d. M0 가 레벨 쪽에서 확인된다 — **가장 작은 레벨이 이미 넘는다** (2026-10-08)

세션 B 의 M0 측정: 방식 A(유닛마다 `Animator`)는 **60~70 개체**에서 8 ms 예산을 다 쓴다
(`docs/M0_CROWD.md`). 500 대 500 과 **한 자릿수가 다르다.**

레벨 쪽에서 같은 결론이 나온다. 검증기에 **최대 병력**(그 판에서 동시에 존재한 최고점)을 넣고
샘플 1-1 을 돌리니:

```
| 경로 | 잔여 | 최대 병력 |
|  LL  |  46  |    75     |   ← 시작 10 · 게이트 둘뿐인 가장 작은 레벨
|  LR  |  41  |    70     |
|  RL  |  16  |    44     |
|  RR  |   0  |    30     |
```

**시작 10 명에 게이트 두 개짜리 레벨이 이미 75 다.** 기획서가 그리는 *"수백 명"* 은커녕
**첫 스테이지도 방식 A 로는 못 그린다.** 즉 방식 B(인스턴싱 + 정점 애니메이션)는 *"나중에 최적화"*
가 아니라 **이 게임이 존재하는 방법**이다.

**왜 평균이 아니라 최고점을 세는가**: 렌더링 예산은 **한 번만 넘어도** 그 프레임이 무너지고,
그 순간은 보통 **증식 직후** — 이 장르에서 **가장 보여 주고 싶은 장면**이다. 평균으로 보면
그 프레임이 평균에 묻힌다.

**`RenderCap` 은 아직 0(검사 꺼짐)이다.** 방식 B 가 측정되면 그 수를 넣고, 그때부터 검증기가
*"이 레벨은 그릴 수 없다"* 를 **레벨을 만들 때** 말해 준다 — 빌드해서 폰에서 알게 되는 대신.

코드를 쓰기 전에 답이 있어야 하는 것만. 나머지는 플레이해 보고 정한다.

| | 질문 | 권고 |

## 5. 만드는 순서

기획서 §15 의 6 주 로드맵을 **검증 가능한 단위**로 다시 끊었다. 각 칸은 *"무엇이 되면 끝인가"* 가
숫자로 적혀 있어야 한다 — 안 그러면 "대충 됐다" 로 넘어가고 그 빚은 5 주차에 돌아온다.

| | 만드는 것 | 끝났다고 말할 수 있는 조건 |
|---|---|---|
| **M0** | 군중 이동만 | 아군 500 + 적 500 · 실기 30fps · 메모리 안 샘 |
| **M1** | 로직 코어 (Unity 없이) | 레벨 하나를 **콘솔에서** 끝까지 돌려 잔여 병력이 나온다 |
| **M2** | 조작 + 게이트 | 드래그로 좌우 · 게이트 그룹이 **한 번만** 발동 · 리더 중심 판정 |
| **M3** | 전투 | 적 군단과 충돌해 양쪽이 줄고, 전멸하면 전진 재개 |
| **M4** | 레벨 검증 도구 | 한 레벨의 **모든 게이트 경로**를 돌려 최적/일반/실패를 출력 |
| **M5** | 10 스테이지 + UI | §6.2 의 학습 순서대로 · 각 스테이지가 M4 로 세 경로 검증 통과 |
| **M6** | 연출 · 사운드 · QA | 기획서 §15.2 체크리스트 |

**M4 가 M5 보다 앞에 있는 것이 이 순서의 요점이다.** 레벨 10 개를 손으로 만들고 나서 검증 도구를
만들면, 그 도구가 처음 알려 주는 것은 *"지금까지 만든 10 개가 틀렸다"* 이다.

- **구체적 수치** (속도·사거리·공격 간격·게이트 값) — 기획서의 초기값으로 시작해 M3 에서 조정한다.
  지금 정해 봐야 플레이 전이라 근거가 없다
- **수익화** — 게임 루프가 재미있다는 것이 확인되기 전에는 설계하지 않는다 (기획서 §14 동의)
